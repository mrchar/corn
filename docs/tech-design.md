> 版本：v0.1

## 1. 背景与约束

### 1.1 来自领域设计的约束

以下业务语义直接决定技术方案，不可绕过：

| 领域约束                                | 技术含义                                           |
| --------------------------------------- | -------------------------------------------------- |
| 空间硬隔离                              | 数据与权限按空间强制隔离，跨空间零可见             |
| 领域解耦：跨领域只读，写入仅经事件驱动  | 写入路径必须走事件，不能提供跨领域改写接口         |
| 数量不可直接改写，一切由不可变流转推导  | 账本 append-only；数量口径为派生视图，不落可写字段 |
| 资源类型可扩展 + 内建模板可启用         | **元数据在运行时可变**，接口形状随空间而异         |
| 事件驱动 + 定时触发                     | 需要事件总线与调度器                               |
| 权限：角色权限基座 + 面向用户的属性策略 | 判定分两阶段，且策略由领域定义、群组套用           |
| 占用可释放或结算为花费                  | 占用是有生命周期的实体，不是一次性写操作           |

### 1.2 来自前端组件库的约束

前端采用自研组件库 `@mrchar/cumquat`（详见第 2 章）。它自带**元数据驱动的资源池**，因此对后端提出的不是"随便一套 REST"要求，而是一组具体契约（见第 3 章）。**这套契约是本项目后端选型的决定性因素**。

## 2. 前端接入现状

### 2.1 技术栈与架构

- Vue 3 + TypeScript；pnpm monorepo；Vite 构建；Node ≥22；ESM。
- 三层架构：**composables**（headless 逻辑层，仅依赖 Vue 运行时）→ **components**（默认渲染壳）→ **themes**（`cq-` 语义 token）。
- 核心原则：**逻辑与渲染解耦，组件自身不发请求**——一切异步能力通过协议由宿主注入。

### 2.2 三大异步协议

| 协议        | 用途                               | 宿主需要提供                                 |
| ----------- | ---------------------------------- | -------------------------------------------- |
| `fetch`     | 组件主动查询（分页、关键词、排序） | 一个 `(query) => Promise<数据或信封>` 的函数 |
| `action`    | 交互动作（提交、释放、结算）       | 一个返回 `Promise<ActionResult>` 的函数      |
| `subscribe` | 被动订阅外部推送                   | 一个持续产出数据的订阅源                     |

### 2.3 统一契约

三个最小类型，不绑定任何 HTTP 细节：

- `AsyncStateLike<T>`：`status`(pending/success/error) + `data` + `error` + `isStale` + `retry`
- `ActionResult`：`status` + `error` + `message`
- `SubscribeResult<T>`：`status`(loading/success/error) + `data` + `error` + `message`

### 2.4 资源池与元数据解析

`useResources` 绑定 **服务端地址 + OpenAPI/Swagger 文档地址**，自动导出资源方法（list / detail / create / update / remove）与字段元数据（columns / properties），并支持自定义解析与微调。

默认解析行为：

- **资源名**：取操作的首个 tag；CRUD 按方法 + 路径形态映射（GET 集合 / GET 单项 / POST 集合 / PUT|PATCH 单项 / DELETE 单项）。
- **列表响应**：识别裸数组，或"数组属性 + 总数属性"信封。
- **查询参数**：分页、关键词、排序各有一组候选名；其余 query 参数自动成为筛选项。
- **字段元数据**：从响应与请求体 schema 提取 `type` / `format` / `enum` / `required` / `description` 等。

### 2.5 组件面

基础、表单控件、浮层、数据展示（表格、分页、树、级联、时间线、步骤、描述列表、进度）、反馈、导航布局——已覆盖本项目绝大多数界面需求。

## 3. 前端对后端的契约要求

1. **必须能低成本产出 OpenAPI 3.x 文档**（含 paths、tags、parameters、requestBody、responses schema）。
2. **贴合 REST 五件套**：`GET 集合` / `GET {id}` / `POST 集合` / `PUT|PATCH {id}` / `DELETE {id}`。
3. **列表响应**为裸数组或 `{ list, total }` 信封；若后端采用其他命名，需在前端做映射。
4. **查询参数名**需落在识别集合内，否则需逐项映射。
5. **`description` / `enum` / `format` / `required` 即 UI**——它们直接变成前端列名、表单标签、下拉选项与校验规则。
6. **写操作**返回体需兼容 `ActionResult`（status / error / message）。
7. **鉴权**通过请求头注入。
8. **必须有推送通道**，以支撑 `subscribe` 协议。
9. **文档需按空间动态生成**——各空间启用的资源类型不同，接口形状随空间而异。

> 结论：后端必须把"产出高质量元数据"当作一等需求，而不是附属产物。

## 4. 后端选型

### 4.1 结论

**TypeScript + NestJS**。

### 4.2 理由

1. **契约同源**：与前端同语言，`description` / `enum` / `format` 只需在 DTO 上维护一次，即可同时供后端生成 OpenAPI 与前端的字段元数据，避免两处维护而漂移。
2. **模块边界天然对应领域边界**：空间、领域、群组、资源类型、资源、账本、规则、投影各自成模块，与 design.md 的章节划分几乎一一对应。
3. **OpenAPI 是框架内建能力**：不依赖额外工具链。
4. **调度与事件生态齐全**：定时触发与事件总线都有成熟支持，契合"定时创建""事件驱动""自然损耗"。
5. **类型安全贯穿全栈**：账本、口径、事件负载均为强类型，重构成本低。

### 4.3 关键选型

| 项         | 选择                                | 理由                                                                 |
| ---------- | ----------------------------------- | -------------------------------------------------------------------- |
| 语言/框架  | TypeScript + NestJS                 | 见 4.2                                                               |
| 元数据产出 | NestJS SwaggerModule + DTO 装饰器   | 内建 OpenAPI 生成                                                    |
| 校验       | class-validator / class-transformer | 与元数据装饰器同源，避免两套定义                                     |
| 数据库     | **PostgreSQL**                      | 事务保证账本与口径一致；约束可表达"可用量非负"；JSONB 承载可扩展属性 |
| 数据访问   | Prisma（备选 TypeORM）              | 类型安全、迁移明确                                                   |
| 调度       | NestJS Schedule                     | 周期注入与自然损耗                                                   |
| 事件       | 进程内事件总线起步，预留外置        | 单体内足够，后续可拆分                                               |
| 推送       | SSE                                 | 单向广播，与 `subscribe` 协议一致                                    |
| 认证       | 自建 Token（待定：接入外部身份源）  | 见第 8 章                                                            |

### 4.4 模块划分

```text
SpaceModule        空间、成员、邀请
DomainModule       领域、领域管理员、领域解耦规则
GroupModule        群组树、群组管理员（套用权限模型）
AccessModule       角色权限判定 + 属性策略判定（两阶段）
ResourceTypeModule 类型元模型、内建模板、启用/继承/改写
ResourceModule     资源实例、数量口径视图
LedgerModule       流转记录、占用生命周期、冲正
AutomationModule   规则、调度器、事件总线
ProjectionModule   投影初始化导入与同步
TagModule          标签键、标签标注
RealtimeModule     SSE 推送
MetadataModule     按空间动态生成 OpenAPI 文档
AuditModule        审计与留痕
```

## 5. 前后端对接机制

### 5.1 隔离上下文：路径前缀

空间是硬隔离边界，因此**把空间放进路径前缀**，每个空间实例化一个独立的资源池：

```text
/spaces/{spaceId}/...
```

前端：

```ts
useResources({
  server: `/spaces/${spaceId}`,
  doc: '/openapi.json',
  headers: () => ({ Authorization: `Bearer ${token}` }),
});
```

领域不作为路径段（领域是软边界、可跨领域只读），而是通过**筛选参数**与**资源归属**体现；跨领域读取由后端在只读视图上放开。

### 5.2 元数据契约：按空间动态生成 OpenAPI

**核心机制**：`GET /spaces/{spaceId}/openapi.json` 返回**该空间当前可用**的接口文档——只包含该空间已启用的内建模板与已定义的自有资源类型。

映射规则：

- **一个资源类型 = 一组 REST 路径 + 一个 tag**；
- 路径段用资源类型的**编码**，tag 用资源类型的**名称**（前端据此得到资源名）；
- 路径中的字段（属性模式）→ schema 属性，其 `description` 写业务中文标签，`enum` 声明枚举值。

```text
GET    /spaces/{spaceId}/budgets            tag: 经费
POST   /spaces/{spaceId}/budgets
GET    /spaces/{spaceId}/budgets/{id}
PATCH  /spaces/{spaceId}/budgets/{id}
DELETE /spaces/{spaceId}/budgets/{id}
```

由于资源类型运行时可变，文档**不能依赖静态注解拼装**，需在 `MetadataModule` 中按空间读取类型定义后构造文档对象再输出。内建模板（成员→人力资源等）同样以资源类型形态出现在文档中。

**收益**：空间管理员启用某个内建模板、或领域管理员定义新资源类型后，前端**无需改代码**即可获得对应的列表、详情与表单——这正是"类型可扩展"落到 UI 的方式。

### 5.3 查询参数与响应约定

| 项       | 约定                                            |
| -------- | ----------------------------------------------- |
| 分页     | `page`（从 1 起）、`pageSize`                   |
| 关键词   | `keyword`                                       |
| 排序     | `sorter`（如 `createdAt,desc`）                 |
| 筛选     | 资源属性逐个作为 query 参数；枚举数组以逗号连接 |
| 列表响应 | `{ list, total }`                               |

若后端希望使用 `pageNo` / `size` / `records` / `totalCount` 等命名，可在前端用参数名映射与响应映射消化，不必迁就前端。

### 5.4 写操作

沿用 REST 五件套（POST / PATCH / DELETE），返回体兼容 `ActionResult`：

```json
{ "status": "success", "message": "已创建" }
```

失败时返回统一错误体（见 5.8），前端自动进入失败分支并提示。

### 5.5 动作型端点（资源池五件套覆盖不到的部分）

占用、释放、结算、花费、查流转不是 CRUD，需单独定义并与前端 `action` 协议绑定：

| 方法 | 端点                                              | 语义                             |
| ---- | ------------------------------------------------- | -------------------------------- |
| POST | `/spaces/{spaceId}/creations`                     | 创建（注入），来源类别随请求声明 |
| POST | `/spaces/{spaceId}/reservations`                  | 创建占用（含持有期）             |
| POST | `/spaces/{spaceId}/reservations/{id}/release`     | 释放占用                         |
| POST | `/spaces/{spaceId}/reservations/{id}/settle`      | 结算为花费                       |
| POST | `/spaces/{spaceId}/consumptions`                  | 直接花费（去向类别随请求声明）   |
| POST | `/spaces/{spaceId}/ledger/{entryId}/reverse`      | 冲正                             |
| GET  | `/spaces/{spaceId}/resources/{resourceId}/ledger` | 流转明细                         |

前端以 `action` 协议绑定这些端点，由组件自动派生 loading / disabled 与错误提示。
资源实例的"可用量"等口径字段应从资源列表接口返回，避免前端自行计算。

### 5.6 推送通道：SSE

```text
GET /spaces/{spaceId}/events        Content-Type: text/event-stream
```

- 频道按事件类别划分：`resource.created` / `resource.reserved` / `resource.released` / `resource.settled` / `resource.consumed` / `resource.adjusted` / `projection.synced` / `domain.event`。
- 事件负载至少包含：空间、领域、资源标识、资源类型、变化量、所属来源或去向类别、触发方式、发生时间、事件标识。
- 前端以 `subscribe` 协议消费；断线重连与"失败保留旧数据"由前端机制承担。
- 该通道同时是**"跨领域只经事件驱动"的落地载体**：领域间的影响只能以事件形式穿透。

### 5.7 鉴权与授权

- **鉴权**：请求头注入 Bearer Token；前端只负责携带，不参与判定。
- **授权**：后端两阶段判定——先由角色权限（空间/领域/群组继承）给出基本能力，再叠加领域管理员定义的属性策略（显式拒绝优先）。
- **前端仅做展示降级**（如无权限时禁用按钮），不作为安全边界。

### 5.8 统一错误体

```json
{
  "status": "error",
  "message": "可用量不足",
  "error": { "code": "INSUFFICIENT_AVAILABLE", "detail": { "available": 1200, "requested": 5000 } }
}
```

`message` 直接用于提示；`code` 供前端做分支处理；`detail` 供表单回填与定位。

### 5.9 契约共享

- 后端 DTO 装饰器同时产出**校验规则**与**OpenAPI schema**，单一事实来源。
- 前端从 OpenAPI 生成 TypeScript 类型（构建期），或直接依赖资源池的运行时元数据（运行期）。
- 两者不冲突：类型用于编译期约束，资源池元数据用于运行期渲染。

## 6. 一致性与并发要点

| 要点       | 做法                                                                  |
| ---------- | --------------------------------------------------------------------- |
| 账本不可变 | `ledger_entries` 只允许插入，冲正以新增记录实现                       |
| 数量口径   | 总量/已占用/已消耗/可用量由流转派生，作为聚合视图或缓存，不落可写字段 |
| 可用量非负 | 事务内校验 + 数据库约束兜底                                           |
| 并发扣减   | 行级锁或乐观锁版本号；写路径串行化到资源实例                          |
| 幂等       | 事件驱动产生的流转携带事件标识，唯一约束防重复消费                    |
| 投影同步   | 内建来源规则监听系统事件后生成流转，与普通流转同一套账本              |
| 定时任务   | 调度触发即生成流转；漏执行需可补执行且可追溯                          |
| 列表性能   | 口径视图物化，避免列表页实时聚合                                      |

## 8. 待定问题

1. **身份认证来源**：自建账号体系，还是接入外部身份源（企业通讯录/单点登录）？影响空间邀请机制。
2. **数据访问层**：Prisma 还是 TypeORM。
3. **多空间隔离在库层的实现**：单库按 `space_id` 过滤，还是按模式/库隔离。
4. **事件总线外置时机**：单体内事件足够还是需要独立消息通道。
5. **SSE 规模化**：多实例部署时的连接与广播方案。
6. **规则引擎**：规则的表达与执行形态（与 design.md 待定项联动）。
7. **属性策略的实现**：策略的存储形式与判定顺序。
8. **资源列表的筛选能力边界**：哪些属性可筛、哪些仅可展示。
9. **元数据文档的缓存策略**：资源类型变更后文档的失效与刷新方式。
