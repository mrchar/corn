## 1. 概述

### 1.1 一句话定义

一个让组织（或多人协作团体）对自己的各类资源进行**统一登记、分配、占用与消耗**的云服务。资源可以是资金、生产资料、人力、办公场所等任何可被计量与分配的东西。

### 1.2 要解决的问题

传统做法里，资金在财务系统、物资在库存系统、人力在排班系统、场所在资产台账，彼此割裂，无法回答"我手上到底还有多少可用的东西、它从哪来、到哪去了"。

本服务把**任意可计量对象**抽象为统一的「资源」，用同一套机制回答三个问题：

- **有多少**——资源当前的总量、可用量与已消耗量；
- **从哪来**——每一次增加都记录明确的来源；
- **到哪去**——每一次减少都记录明确的去向。

### 1.3 三条核心主线

| 主线 | 含义                                   | 关键问题                     |
| ---- | -------------------------------------- | ---------------------------- |
| 创建 | 资源被注入，总量增加                   | 谁/什么触发了这次流入？      |
| 占用 | 资源被预留，可用量减少但总量不变       | 占用了多少？何时释放或结算？ |
| 花费 | 资源被真正消耗，可用量与总量口径上减少 | 因为什么事、以什么方式流出？ |

### 1.4 设计原则

1. **一切变动皆有记录**：资源数量不允许被直接改写，任何数量变化都必须由一条流转记录产生，且能追溯其来源或去向。
2. **类型可扩展而非写死**：系统提供资源的类型元模型，使用者可自行定义资源类型，而不需要系统改动。
3. **隔离与解耦**：空间是完全隔离的边界，跨空间互不可见；领域之间相互解耦，跨领域**只能读取、不能改写**，跨领域的写入只能通过**事件驱动**间接发生。
4. **数量即事实，权限即约束**：数量的真实性由流转保证，能不能做某件事由权限决定。
5. **标记与权限分离**：标签只做标记，系统不赋予其内建语义；系统的权限判定由自身的角色体系保证，更细的权限交由面向用户的开放机制。

## 2. 核心概念与术语

### 2.1 术语表

| 术语       | 别名/英文              | 说明                                                                           |
| ---------- | ---------------------- | ------------------------------------------------------------------------------ |
| 空间       | Space                  | 最外层的完全隔离边界，拥有独立的资源集合与成员                                 |
| 领域       | Domain                 | 空间内的分区；领域之间相互解耦，承载最基础的权限配置                           |
| 群组       | Group                  | 领域下的组织单元，可嵌套，用于归属与批量授权                                   |
| 用户       | User                   | 自然人账号；一个用户可加入多个空间                                             |
| 成员       | Member                 | 用户在某空间（或领域/群组）中的身份与角色                                      |
| 资源类型   | ResourceType           | 对一类资源的定义（计量方式、属性、可分割性等）                                 |
| 资源       | Resource / 资源账户    | 某个资源类型的一个具体载体，持有余额                                           |
| 计量单位   | Unit                   | 资源的度量单位（元、人天、平方米、台…）                                        |
| 流转       | LedgerEntry / 流转记录 | 一次数量变动的不可变记录                                                       |
| 来源       | Source                 | 引起资源增加的原因类别（人工录入 / 定时创建 / 事件驱动）                       |
| 去向       | Sink                   | 引起资源减少的原因类别（手工登记 / 自然损耗 / 事件驱动）                       |
| 占用       | Reservation            | 对可用量的冻结，可释放或结算为消耗                                             |
| 规则       | Rule                   | 描述"在什么条件下自动产生什么流转"的声明                                       |
| 触发器     | Trigger                | 规则的驱动方式：定时触发或事件触发                                             |
| 角色权限   | 权限基座               | 平台内建的权限机制：基于领域与群组的角色与继承，系统自身据此判定一切权限       |
| 属性策略   | 面向用户的开放权限机制 | 用户按属性自定义的补充权限规则；平台权限基座不依赖它                           |
| 权限模型   | —                      | 领域定义的一套可复用授权模型，由角色权限与属性策略构成；群组只能套用、不能改写 |
| 群组管理员 | GroupAdmin             | 群组的管理者，创建群组时指定、可转让；只能在本群组及其子群组树内套用领域模型   |
| 标签键     | TagKey                 | 由领域管理员定义的标签元数据（键名、值类型、枚举值域等）                       |
| 标签标注   | TagAssignment          | 给资源或成员附加的"键＝值"标记                                                 |
| 资源模板   | Template               | 可复用的资源定义，含计量、属性与预置规则 |
| 内建资源模板 | BuiltinTemplate      | 系统预置的资源模板，可据以快速创建资源；覆盖全部组织对象 |
| 投影       | Projection             | 把组织对象映射为资源实例的机制，单向（组织 → 资源） |
| 初始化导入 | —                      | 启用投影时，把既有组织对象一次性导入为资源实例 |

### 2.2 概念关系总览

```text
空间 Space  ──┬── 成员 Member ── 用户 User
              │        └── 标签标注
              ├── 领域 Domain ──┬── 领域管理员（定义权限模型）
              │                 ├── 群组 Group ──┬── 群组管理员
              │                 │                └── 子群组 Group …
              │                 ├── 标签键 TagKey ── 标签标注
              │                 └── 资源 Resource ── 标签标注
              ├── 资源类型 ResourceType ──┬── 内建资源模板（可据以快速创建资源）
              │                          └── 资源 Resource ── 流转 LedgerEntry
              │                                             └── 占用 Reservation
              └── 组织对象投影：空间/领域/群组/成员 ──（投影）──▶ 资源 Resource
```

要点：

- 一个空间下可以有多个领域；一个领域下可以有多个群组；群组可无限层级嵌套。
- 资源类型是空间的配置资产，资源实例归属于一个领域，可进一步归属到群组。
- 流转与占用都挂在具体的资源实例上，是资源数量的唯一变化途径。
- 标签键归属于领域，标签标注只能使用本领域的标签键；资源与成员可被标注，其余对象不可。
- 权限模型由领域定义：领域管理员是**定义者**，群组管理员只能在所负责的群组内**套用**。
- 空间、领域、群组、成员均为**组织对象**，可通过**投影**映射为资源实例（见 6.5–6.7）。

## 3. 组织结构与隔离模型

### 3.1 层级结构

```text
空间 Space（完全隔离）
 └── 领域 Domain（相互解耦：跨领域只读，写入仅经事件驱动）
      └── 群组 Group（可嵌套）
           └── 子群组 Group
                └── …
```

其中成员、群组、领域、空间都是**组织对象**，可通过投影映射为资源实例（见 6.5–6.7）。

### 3.2 空间：完全隔离的边界

空间的语义是**硬隔离**：

- 每个空间拥有独立的成员名单与独立的资源集合；
- 不同空间可以邀请不同的用户加入，也可以邀请同一用户加入多个空间，但该用户在两个空间中的身份、角色、可见数据互不相通；
- **跨空间默认不可见、不可授权、不可引用**。同一个人在 A 空间的资源，B 空间的成员无从知晓；
- 空间是权限继承链的根，也是计费、审计、数据导出的最外层单位。

邀请机制：空间成员（通常为空间管理员）向用户发出邀请，用户接受后成为该空间的成员。同一资源集合由该空间内的成员共同使用。

### 3.3 领域：相互解耦的软边界

领域在空间内部承担三个职责：

1. **定义本领域的权限模型**——权限的最小配置单位落在领域上，领域管理员在此定义由角色与属性策略构成的可复用授权模型，而不是逐个资源逐个配置；
2. **建立分类与关联**——领域之间可以存在分类与引用关系（例如"采购"领域与"仓储"领域的资源概念相通）；
3. **定义本领域可用的标签键元数据**——标签能否使用、以何种形式使用，由领域管理员在此定义（见第 5 章）。

与空间的区别：

- 空间之间**不允许**任何数据流动；
- 领域之间**相互解耦**：跨领域**只能读取，不能改写**；跨领域若需产生写入，只能通过**事件驱动**间接完成，不存在直接跨领域改写。

**领域管理员**：每个领域可以单独配置管理员。领域管理员在本领域范围内拥有管理权（**定义权限模型**、成员配置、群组管理、资源类型与资源的管理、标签键定义），但不会自动获得其他领域或空间级别的权力。

### 3.4 群组：可嵌套的组织单元

- 群组是领域下的组织单元，用于把成员按职责、项目或团队归拢；
- **群组可相互嵌套**，形成树形结构；子群组默认继承父群组的授权；
- 一个成员可以同时属于同领域的多个群组；
- 群组不产生新的隔离边界，只影响**归属**与**授权范围**。

**群组管理员**：

- 每个群组有其管理员；群组**创建时指定**管理员，管理员身份**可以转让**；
- 顶层群组由领域管理员创建并指定其管理员；群组管理员可在自己管辖的子树内创建子群组并指定子群组管理员；
- 群组管理员的管理范围**覆盖本群组及其整个子群组树**；
- 群组管理员**只能套用**领域定义的权限模型（把已有角色/策略分配给本群组成员），**不能新增角色或策略**——模型的改写权只在领域管理员。

群组嵌套的权限语义：授权沿父 → 子 单向继承；在子群组上可以调整已有角色/策略的分配范围，但不得超出领域的权限模型。

### 3.5 三种边界对比

| 维度                 | 空间                 | 领域                                 | 群组                                 |
| -------------------- | -------------------- | ------------------------------------ | ------------------------------------ |
| 隔离强度             | 完全隔离             | 解耦，仅可读取                       | 无隔离，仅归属与授权                 |
| 能否跨边界共享资源   | 否                   | 只能读取、不能改写；写入仅经事件驱动 | 是（同一领域内天然共享）             |
| 是否可嵌套           | 否（平级）           | 否（平级）                           | 是                                   |
| 权限配置粒度         | 最高层（成员与角色） | 基础权限落点                         | 授权范围落点                         |
| 是否可定义标签键     | 否                   | 是                                   | 否                                   |
| 是否可定义权限模型   | 否                   | 是（领域管理员定义）                 | 否（群组管理员只能套用）             |
| 是否可独立配置管理员 | 是（空间管理员）     | 是（领域管理员）                     | 是（群组管理员，创建时指定、可转让） |

## 4. 权限模型

权限由**领域定义的一套权限模型**统一承载。模型中包含两种手段：**角色权限**（平台内建的权限基座，系统自身用它判定一切权限）与**属性策略**（面向用户开放的补充机制，用户按属性自定义）。

模型遵循**定义权与使用权分离**：**领域管理员定义模型**，**群组管理员只能套用模型**、不能改写。

### 4.1 权限基座：角色权限

权限判断统一为三元式：**主体** 在 **作用域** 上拥有 **某项操作** 的能力。

- **主体**：用户（经成员身份生效），或群组。
- **作用域**：空间 / 领域 / 群组。
- **操作**：见 4.3 操作清单。

系统自身的权限判定完全依据这一层。

### 4.2 角色与继承

- **空间层角色**：空间所有者、空间管理员、普通成员、访客（只读）。
- **领域层角色**：领域管理员、领域成员。
- **群组层角色**：群组管理员（唯一固定角色，管理本群组及其整个子群组树）；其余权限通过授予具体操作来表达。

继承规则：

```text
空间权限 ──继承──▶ 领域权限 ──继承──▶ 群组权限 ──继承──▶ 子群组权限
```

- 上级已有的权限，下级自动具备；
- 下级只能**追加**权限，或对上级授予的权限做**显式收窄**；
- 下级不能反向提升上级权限。

### 4.3 操作清单

权限按操作而非"角色名"表述，角色只是操作的预设组合。

| 类别     | 操作                                                 | 说明                                                       |
| -------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| 资源类型 | 定义类型 / 修改类型 / 停用类型                       | 影响该类型下全部资源                                       |
| 资源     | 创建资源 / 查看资源 / 归档资源                       | 资源实例的增删查                                           |
| 数量变动 | 创建（注入） / 占用 / 释放占用 / 花费 / 调整         | 见第 7、8 章                                               |
| 标签     | 定义标签键 / 标注资源与成员                          | 标签键的定义权在领域管理员                                 |
| 自动化   | 定义规则 / 启用停用规则                              | 定时与事件驱动配置                                         |
| 组织     | 定义权限模型 / 套用权限模型                          | 定义权在领域管理员；套用权在群组管理员，仅限本群组及其子树 |
| 组织     | 创建群组 / 指定或转让群组管理员 / 管理本群组及其子树 | 顶层群组由领域管理员创建，子群组由上级群组管理员创建       |
| 组织     | 管理成员 / 管理领域                                  | 成员与领域层面的组织维护                                   |
| 审计     | 查看流转明细 / 导出                                  | 追溯能力                                                   |

### 4.4 角色权限的判定要点

1. **先隔离、再授权**：任何判定都先确认主体与该资源属于同一空间，否则直接拒绝。
2. **领域是最小配置单位**：批量授权落在领域上，避免逐资源授权。
3. **占用与花费可分别授权**：允许"可以占用但不能花费""可以花费但需更高权限"这类区分。
4. **越权不可传递**：在 A 领域的管理权不代表在 B 领域有管理权。
5. **定义权与使用权分离**：权限模型只能由领域管理员定义或改写；群组管理员只能在本群组及其子树内套用，不得新增角色或策略。
6. **跨领域只读**：跨领域访问一律降级为只读，任何跨领域写入都必须经事件驱动间接完成。
7. **只读兜底**：成员默认至少具备本空间内可见资源的查看权。

### 4.5 面向用户开放的属性策略

- **定位**：属性策略是**开放给用户的权限管理机制**，让用户在平台角色权限之外，按属性自定义更细的授予与限制。
- **与基座的关系**：**叠加而非替代**。系统本身始终以角色权限为准；属性策略只是用户自定义的补充约束，不改变基座的判定。
- **属性来源**：主体属性（成员标签、角色、所属群组）、资源属性（资源标签、所属类型、所属领域）、环境属性（时间等）。
- **生效边界**：属性策略是权限模型的组成部分，由**领域管理员在本领域内定义**；**群组管理员只能在本群组及其子树内套用**，不得新增策略。策略不跨领域、不跨空间，空间硬隔离不被任何策略突破。
- **判定次序**：角色权限给出基本能力；若有命中的属性策略，则在其上叠加（显式拒绝优先）。
- **细则延后**：属性策略的具体表达方式与规则引擎一并后续设计，本文只登记其定位与边界（见第 12 章）。

## 5. 标签机制

### 5.1 定位

标签是一个**纯标记系统**：它只用来给对象附加"键＝值"的说明性信息。**系统自身不赋予标签任何内建语义**——标签不参与权限判定、不影响资源数量、不触发任何流转。标签的用途完全由使用者自行定义；未来用户自定义的规则可以引用标签作为匹配条件（规则引擎另行设计，见第 12 章）。

### 5.2 标签键（元数据）

标签键由**领域管理员**在本领域内定义，是标签能否使用的前提。一个标签键包含：

| 要素     | 含义                                   |
| -------- | -------------------------------------- |
| 键名     | 标签的名称，如"部门""用途""安全级"     |
| 值类型   | 文本 / 数值 / 枚举 / 布尔              |
| 枚举值域 | 当值类型为枚举时，预先定义的允许取值   |
| 是否必填 | 标注时该键是否为必需                   |
| 是否多值 | 一个对象在该键下能否填多个值           |
| 校验规则 | 非枚举类型时的格式约束（长度、范围等） |

### 5.3 标签值的填写

- **值类型为枚举时，标注只能从预定义的枚举值中选择**；
- 其余类型（文本 / 数值 / 布尔）由成员在符合校验规则的前提下**自由填写**。

### 5.4 标注对象

标签只能标注两类对象：

- **资源实例**；
- **成员**。

群组、领域、空间、资源类型等对象不参与标签标注。

### 5.5 作用域与隔离

- 标签键归属于领域，**不跨领域**：对象的标注只能使用相关领域的标签键；
- 资源标注以资源**所属领域**为作用域；
- 成员标注以**领域**为作用域：同一成员在不同领域下可以有各自的标注；
- 标签整体**不跨空间**，空间硬隔离优先；
- 跨领域读取时，标签随被读对象一并展示（只读），不得据此外领域改写。

### 5.6 生命周期

- 标签键可**停用**：停用后不能再新增标注，但**既有标注保留、不受影响**；
- 标签键可**删除**：删除同样**不影响既有标注**，既有标注继续以历史记录形式存在；
- 标注本身可增删改，其变更是否需要留痕见第 12 章待定。

## 6. 资源类型系统与内建资源

### 6.1 设计意图

系统提供一套**元模型**，使用者在空间内自行定义资源类型；同时预置一批**内建资源模板**（见 6.5），使用者可据以快速创建资源。这样新增一类资源无需系统改动，常见资源也无需从零定义。

### 6.2 类型定义包含的要素

| 要素           | 含义                                                   | 示例                                      |
| -------------- | ------------------------------------------------------ | ----------------------------------------- |
| 类型名称与编码 | 类型的标识                                             | "运维经费" / `ops.budget`                 |
| 计量单位       | 度量单位                                               | 元、人天、平方米、台                      |
| 数值形态       | 整数 / 小数、精度、是否允许小数拆分                    | 金额保留 2 位小数；人数为整数             |
| 可分割性       | 能否被拆成更小份额使用                                 | 经费可分割；一台设备不可分割              |
| 允许负值       | 数量是否允许出现负数                                   | 通常不允许；允许透支时开启                |
| 属性模式       | 该类型资源需要携带的业务属性                           | 场所的"地址"、人力的"职级/技能"           |
| 生命周期       | 是否有有效期/折旧等时间属性                            | 办公用品有保质期；设备有折旧              |
| 来源方式       | 允许哪些来源类别                                       | 经费：人工录入 + 事件驱动；工时：定时创建 |
| 去向方式       | 允许哪些去向类别                                       | 设备：自然损耗 + 事件驱动                 |
| 推荐标签键     | 建议该类型资源使用的标签键（键的定义权仍在领域管理员） | 场所建议使用"位置""面积"                  |
| 默认归属       | 新资源默认落到哪个领域/群组                            | 默认归入创建者所在领域                    |

### 6.3 三种典型形态

按数量随时间的变化特征，资源可分为：

- **存量型**：总量累积、消耗后减少（经费、物资、场所容量）。
- **周期型**：按周期重置或补充（每月的预算额度、每周的可用工时）。
- **时点型**：只在特定时刻有意义（某天的人手、某台设备在某时段可用）。

三种形态共用同一套流转机制，差异主要体现在**默认触发器**与**周期规则**上。

### 6.4 类型的变更约束

- 类型**已存在资源实例**时，计量单位、数值形态、可分割性等影响既有数据口径的要素**不可直接修改**，只能停用旧类型、新建新类型；
- 名称、属性模式中"只新增属性"的部分可以演进；
- 停用类型不删除既有资源，仅阻止新建该类型的资源。

### 6.5 内建资源模板

系统预置一批**资源模板**，即"开箱可用的资源定义"，包含该资源的计量方式、属性、可分割性以及**预置规则**（初始化导入规则、来源同步规则等）。

- **覆盖全部组织对象**：成员 → 人力资源，群组 → 组织资源，领域、空间 → 对应的组织/场所类资源；
- **据模板快速创建**：使用者可直接套用模板创建资源，无需从零定义类型与规则；
- **模板本身只读**：模板由系统维护，使用者不能修改模板内容，只能"套用"，或据其在本领域内改写。

### 6.6 启用、继承与改写

内建模板机制分三层落地：

| 层级 | 决定 |
| --- | --- |
| 空间管理员 | 配置本空间**是否启用**各项内建模板机制；未启用的模板在该空间内不可使用 |
| 领域管理员 | 对已启用的模板，决定**继承**还是**改写** |

- **继承**：沿用模板给出的定义与预置规则，快速创建资源并自动获得投影与同步能力；
- **改写**：在本领域内改写这些规则，形成本领域自己的定义；
- **本质相同**：继承与改写都是对**领域内规则**的取舍——沿用模板规则即继承，改写规则即改写，二者不是两条并列路径。

### 6.7 投影

- **投影**：把组织对象映射为资源实例的机制，方向**单向**（组织 → 资源，不反向改写组织对象）；
- **初始化导入**：启用投影时，把当前既有的组织对象**一次性导入**为资源实例，作为初始存量；
- **后续同步**：由**内建来源规则监听系统自身的事件**完成（如"成员加入"事件 → 创建对应人力资源；"成员退出"事件 → 花费或归档）；
- **改写后不保留投影绑定**：领域管理员改写定义后，**原投影绑定不再保留**；此后是否继续联动，完全由领域管理员自行创建的规则决定。

## 7. 资源模型

### 7.1 资源实例

一个资源实例是某类型的一个具体载体，可理解为该类型下的一个"账户"。例如：

- 类型「经费」下的实例："2026 市场部运维经费"
- 类型「人力」下的实例："张三的可用工时"
- 类型「办公场所」下的实例："A 座 3 层会议室整层"

资源实例携带自己的归属（领域、可选群组）、业务属性（依类型定义）、**标签集合**与当前数量状态。

### 7.2 数量状态模型

资源数量分为四个口径，全部由流转记录推导，**不允许直接赋值**：

| 口径   | 含义                         |
| ------ | ---------------------------- |
| 总量   | 历史上所有注入的累计量       |
| 已占用 | 当前处于冻结状态的占用量之和 |
| 已消耗 | 历史上所有花费的累计量       |
| 可用量 | 总量 − 已占用 − 已消耗       |

```text
总量     = Σ 创建流动
已占用   = Σ 活跃占用
已消耗   = Σ 花费流动
可用量   = 总量 − 已占用 − 已消耗
```

### 7.3 关键约束

1. 可用量**不得为负**（除非类型显式允许透支）；
2. 占用与花费之和**不得超过当前可用量**；
3. 总量只增不减（撤销等场景通过"反向流转 + 审计留痕"实现，而非直接改数）；
4. 每个资源实例的任一时刻快照，都能由流转序列完整复现。

## 8. 流转模型：来源与去向

### 8.1 流转记录

每一次数量变化都是一条**不可变的流转记录**，至少包含：发生了多少、对哪个资源、发生在何时、属于哪一类来源/去向、由什么触发、由谁发起、关联的业务事件是什么。

流转不可修改、不可删除，只能通过追加记录修正（冲正）。

**标签不参与数量变化**：给资源增减标签标注不会产生任何流转记录。

### 8.2 来源（增加）

| 来源类别 | 触发方式           | 典型场景                                             |
| -------- | ------------------ | ---------------------------------------------------- |
| 人工录入 | 成员手工登记       | 财务拨款到账、采购物资入库                           |
| 定时创建 | 规则按周期自动注入 | 每月自动发放预算、每周自动补充工时                   |
| 事件驱动 | 由业务事件触发     | 合同签署完成 → 自动生成对应经费；项目立项 → 分配人力 |
| 内建来源 | 系统预置规则监听系统自身事件 | 成员加入 → 创建对应人力资源；群组创建 → 创建组织资源 |

### 8.3 去向（减少）

| 去向类别 | 触发方式       | 典型场景                                     |
| -------- | -------------- | -------------------------------------------- |
| 手工登记 | 成员手工登记   | 报销核销、物资领用、会议室占用转结           |
| 自然损耗 | 时间驱动的规则 | 设备折旧、耗材过期、场所使用时间流逝         |
| 事件驱动 | 由业务事件触发 | 项目结项 → 释放剩余人力；设备报废 → 冲减资产 |

### 8.4 占用与花费的区别

| 维度     | 占用                           | 花费                     |
| -------- | ------------------------------ | ------------------------ |
| 数量变化 | 只影响可用量，总量不变         | 影响可用量，并计入已消耗 |
| 可逆性   | 可释放，归还可用量             | 不可逆，只能冲正         |
| 时间性   | 带明确的持有期                 | 一次性生效               |
| 后续动作 | 释放，或**结算**为花费         | 无                       |
| 典型场景 | 预留预算、锁定人手、预定会议室 | 实际支出、领用、损耗     |

**占用生命周期**：

```text
创建占用 ──▶ 活跃 ──┬──▶ 释放（归还可用量）
                    └──▶ 结算（转为花费，计入已消耗）
                    （超期未处理可自动按规则释放或结算）
```

### 8.5 触发方式与发起者

一条流转必须能回答"是谁或什么造成的"：

- **人工**：由某个成员发起，记录操作者身份；
- **定时**：由规则调度发起，记录规则标识；
- **事件**：由业务事件发起，记录事件标识与事件源。

三类来源/去向与三种触发方式的组合关系由资源类型在元模型中声明（见 6.2）。

## 9. 自动化机制

### 9.1 规则

规则描述"**在什么条件下**，**对哪些资源**，**产生多少**，**以什么方式**的流转"。一条规则包含：

- 作用对象：资源类型或具体资源、所属领域/群组；
- 触发条件：时间条件（周期、时点、区间）或事件条件（事件类型、匹配条件）；
- 匹配条件：可引用资源属性、成员属性与**标签**（标签的引用方式由规则引擎定义，另行设计）；
- 动作：创建 / 占用 / 花费，及数量表达式（可为固定值、按属性计算、按比例）；
- 约束：次数上限、有效期、是否需人工确认；
- 内建来源规则：随内建资源模板提供的**系统预置规则**，监听系统自身事件完成投影同步（见 6.5–6.7）。

### 9.2 定时触发

- 支持周期表达式（每日/每周/每月/自定义间隔）与固定时点；
- 适用于周期型与自然损耗型资源；
- 到期未执行需记录"漏执行"并支持补执行策略。

### 9.3 事件触发

- 监听系统内的业务事件，或接受外部业务系统推送的事件；
- 事件与规则通过"事件类型 + 匹配条件"绑定；
- 同一事件可触发多条规则，需保证可追溯（每条流转记录指向原始事件）。

### 9.4 规则的生效边界

- 规则的作用范围**不得跨越空间**；
- 跨领域不得直接改写：若需在另一领域生效，只能由该领域的事件驱动间接完成（见 3.3）；
- 规则的启用、停用、修改都需要权限与审计。

## 10. 关键业务规则与约束汇总

1. **数量即流转之果**：不存在"直接设置数量"的操作，一切数量变化都产生流转记录。
2. **空间硬隔离**：资源、成员、规则、标签均不跨空间流动。
3. **领域解耦**：跨领域只能读取、不能改写；跨领域写入只能经事件驱动间接完成，不存在直接跨领域改写。
4. **标签为纯标记**：标签不参与权限判定、不影响资源数量、不触发流转；系统不赋予其内建语义。
5. **权限基座唯一**：系统权限由角色权限（基于领域与群组）判定；属性策略仅为面向用户的补充，不替代基座。
6. **权限模型定义权与使用权分离**：模型只能由领域管理员定义或改写；群组管理员只能在本群组及其子树内套用模型，不得新增角色或策略。
7. **占用不消耗，花费不归还**：二者语义严格区分，占用可释放或结算。
8. **可用量非负**：默认不允许超额占用/花费，透支需类型显式开启。
9. **权限向下继承，调整受模型约束**：上级权限下级自动具备；下级的调整只能在领域权限模型范围内进行。
10. **类型口径不可变更**：影响既有数据口径的类型要素一经使用即冻结。
11. **一切自动流转可追溯**：定时与事件驱动的流转必须能定位到规则与事件来源。
12. **流转不可篡改**：只能追加或冲正，历史永续保留。
13. **内建模板可继承可改写**：内建资源模板由系统预置；空间管理员决定是否启用，领域管理员决定沿用模板规则（继承）或改写规则（改写）——继承与改写的本质都是对领域内规则的取舍。
14. **投影单向且由规则驱动**：投影仅在启用时初始化导入，后续同步由内建来源规则监听系统事件完成；改写后**不保留投影绑定**，是否继续联动取决于领域自行创建的规则。

## 11. 典型场景

### 11.1 每月经费自动发放与报销

```text
经费类型（存量型，单位：元，可分割，来源含"定时创建"，去向含"手工登记"）
   │
   ├─ 规则：每月 1 日 09:00 向「市场部运维经费」创建 50000 元
   │
   └─ 成员占用 8000 元用于活动预支 ──▶ 活动结束后结算为花费 7600 元，释放 400 元
```

### 11.2 物资入库与自然损耗

```text
办公用品类型（存量型，有保质期）
   ├─ 采购入库：人工录入创建 200 件
   ├─ 领用：手工登记花费 30 件
   └─ 自然损耗：规则每日检查，临期未领用按比例花费
```

### 11.3 人力在项目间的流转

```text
人力类型（周期型，单位：人天，来源含"定时创建"）
   ├─ 每周一自动补充「张三的可用工时」5 人天
   ├─ 项目立项事件 ──▶ 自动占用 3 人天（事件驱动）
   └─ 项目结项事件 ──▶ 释放剩余人天（事件驱动）
```

### 11.4 跨领域协作（只读 + 事件驱动写入）

```text
空间：某公司
 ├─ 领域：采购 ── 领域管理员 A
 └─ 领域：仓储 ── 领域管理员 B
        │
        └─ 解耦：仓储成员可只读查看采购领域资源与标签；
           若需在采购领域产生变动，只能由采购领域的事件（如"入库完成"）驱动，
           不得直接跨领域改写
```

### 11.5 标签 + 属性策略

```text
领域：运维
 ├─ 标签键：用途（枚举：生产 / 测试 / 办公）、安全级（枚举：公开 / 受限）
 ├─ 资源「机房服务器机柜」标注 ─ 用途 = 生产
 └─ 成员「实习生」标注 ─ 安全级 = 受限
        │
        └─ 属性策略（领域管理员定义，叠加在角色权限之上）：
           主体安全级 = 受限 且 资源用途 ≠ 办公 ──▶ 拒绝「花费」
           （系统仍以角色权限为准，标签与策略只是用户自定义的补充）
```

## 12. 待定问题

以下为设计尚未收敛、需进一步讨论的点：

1. **规则引擎**：规则的表达能力、数量表达式形态，以及**标签如何作为匹配条件被引用**——待专门设计。
2. **属性策略细则**：策略的语言形态、与角色权限的叠加与拒绝优先级、命中多条策略时的裁决顺序。
3. **审批**：占用/花费是否引入审批流？若引入，审批属于领域配置还是资源类型配置？
4. **占用超期处理**：默认自动释放还是自动结算，是否需要按类型分别配置？
5. **跨空间协作**：是否存在"空间间只读镜像"这类受控例外？当前设计为完全不可见。
6. **资源合并与拆分**：可分割资源是否需要显式的合并/拆分操作，还是仅靠流转表达？
7. **群组权限收窄的表达方式**：如何在授权时清晰表达"收窄"而不产生歧义？
8. **标签变更留痕**：标签标注的增删改是否需要审计留痕？标签键的变更是否需要版本化？
9. **审计与冲正的时效**：冲正记录的时间窗口与限制条件。
